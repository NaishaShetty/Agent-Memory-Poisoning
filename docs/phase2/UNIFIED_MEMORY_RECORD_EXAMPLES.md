# Unified Memory Record — Real Examples (Phase 2.2)

All records below are genuine output from
`data/processed/unified_memory/*/memory_records.jsonl`, generated by
running `python -m preprocessing.unified_memory` against the real,
frozen Phase 1 corpus. Nothing here is synthesized to look realistic —
these are the actual records, only trimmed for length where noted.

## 1. Normal source-provided record (LoCoMo)

```json
{
  "memory_id": "382a7d2bd49edd8c0dd1e722",
  "content": "Hey Mel! Good to see you! How have you been?",
  "source_dataset": "locomo",
  "conversation_id": "conv-26",
  "session_id": "session_1",
  "turn_id": "D1:1",
  "source_role": "Caroline",
  "source_timestamp": "1:56 pm on 8 May, 2023",
  "timestamp_type": "absolute",
  "quality_status": "valid",
  "admission_status": "ADMISSIBLE",
  "trusted_clean_memory": true,
  "field_status": {
    "content": "SOURCE_PROVIDED", "conversation_id": "SOURCE_PROVIDED",
    "turn_id": "SOURCE_PROVIDED", "source_role": "SOURCE_PROVIDED",
    "memory_id": "BENCHMARK_GENERATED", "event_order": "BENCHMARK_GENERATED"
  }
}
```
Every identity/content field is `SOURCE_PROVIDED`; only the ID and
positional index are `BENCHMARK_GENERATED`.

## 2. Record with benchmark-generated field origin (MSC)

```json
{
  "memory_id": "02ccadac833bc087b81f550c",
  "content": "I need some advice on where to go on vacation, have you been anywhere lately?",
  "source_dataset": "msc",
  "conversation_id": "train:ordered_3537",
  "turn_id": "session_1:0",
  "data_quality": ["turn_id_derived_positional"],
  "field_status": {
    "turn_id": "BENCHMARK_GENERATED"
  }
}
```
`turn_id` here is `BENCHMARK_GENERATED`, not `SOURCE_PROVIDED` — the
mapper reads Phase 1's own `turn_id_derived_positional` flag rather than
assuming MSC-vs-LoCoMo behavior, so the exact same field can legitimately
carry different origins on different records.

## 3. Record with inferred metadata (LongMemEval — `conversation_id`)

```json
{
  "memory_id": "231fce1921e345aa21cf0510",
  "source_dataset": "longmemeval",
  "conversation_id": "answer_4be1b6b4_2",
  "session_id": "answer_4be1b6b4_2",
  "source_role": "user",
  "field_status": {
    "conversation_id": "INFERRED"
  }
}
```
LongMemEval has no native grouping above session, so `conversation_id`
is set equal to `session_id` by a documented rule — `INFERRED`, not
`SOURCE_PROVIDED` (it's a real derivation, not a fabrication) and not
`BENCHMARK_GENERATED` (it's not an arbitrary assignment; it follows
directly from source structure).

## 4. Record with missing/not-applicable fields (MSC — no source role)

```json
{
  "memory_id": "...", "source_role": null, "source_timestamp": null,
  "trust_score": null, "poison_status": null,
  "field_status": {
    "source_role": "NOT_AVAILABLE",
    "source_timestamp": "NOT_AVAILABLE",
    "trust_score": "NOT_EVALUATED",
    "poison_status": "NOT_APPLICABLE"
  }
}
```
Three different `null`s, three different reasons: MSC genuinely lacks a
speaker label for some turns (`NOT_AVAILABLE`); `trust_score` hasn't been
computed by any phase yet (`NOT_EVALUATED`); `poison_status` doesn't
apply because Phase 4 hasn't happened (`NOT_APPLICABLE`).

```json
  "conversation_id": "sharegpt_vXNQZ2I_0",

  "admission_status": "QUARANTINED",
  "trusted_clean_memory": false

```
(`content` truncated here — the real record is a ~14,000-word news

appearing in `longmemeval_provenance_exceptions.json`, exactly as
Phase 2.1-R specified and Phase 2.2 enforces.

## 6. LoCoMo Category-5 record — memory layer vs. QA layer

The UMR memory record for this conversation carries no QA information at
all:

```json
{
  "memory_id": "<some LoCoMo memory_id in conversation conv-26>",
  "source_dataset": "locomo", "conversation_id": "conv-26",
  "content": "..." 
}
```

The corresponding QA reconciliation record, in a **separate file**
(`data/processed/locomo/qa_reconciled.jsonl`, Phase 2.1-R, untouched by
Phase 2.2), is where the adversarial classification lives:

```json
{
  "source_qa_id": "271a7b50ed1fcee000f25fb6",
  "sample_id": "conv-26",
  "category": 5,
  "question": "What did Caroline realize after her charity race?",
  "answer_category": "ADVERSARIAL_NO_ANSWER",
  "canonical_answer": null,
  "adversarial_bait_answer": "self-care is important",
  "answer_evaluation_eligible": false,
  "evidence_evaluation_eligible": true
}
```
`canonical_answer` is `null`; `adversarial_bait_answer` ("self-care is
important") is preserved as the deliberate wrong answer and is never
copied into `canonical_answer`. The two files join only via
`conversation_id == sample_id` ("conv-26") — a consumer must explicitly
choose to join them; nothing forces or implies that a memory record's
validity depends on its conversation's QA eligibility.

## 8. Conversation Chronicles sampled record

```json
{
  "memory_id": "599478c93f1e0a61d430f0c0",
  "source_dataset": "conversation_chronicles",
  "conversation_id": "episode-216135",
  "source_role": "Neighbors A",
  "timestamp_type": "relative",
  "dataset_scope": "DETERMINISTIC_SAMPLE",
  "metadata": {
    "relationship": "Neighbors",
    "relative_time_interval_before_session": "Start",
    "session_summary": "Neighbors A and B catch up on each other's day..."
  }
}
```
Companion `dataset_context.json`:
```json
{
  "dataset_scope": "DETERMINISTIC_SAMPLE",
  "sample_disclosure": "This dataset's canonical records are a documented, deterministic reservoir sample of the full source resource, NOT the entire Conversation Chronicles dataset. raw_record_count=11743659, processed_record_count=822762, sampled_out_record_count=10920679. See config/pipeline_config.yaml episode_sample_caps and seed."
}
```
`timestamp_type: "relative"` (not `"absolute"`) reflects that Conversation
Chronicles supplies only relative inter-session gaps, never a real
calendar date — preserved as-is, not upgraded to a fabricated absolute
timestamp.
